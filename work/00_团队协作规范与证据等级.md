# 团队协作规范与证据等级（所有成员必读）

日期：2026-11-06　适用：长城 Agent 框架设计项目

## 0. 本项目的性质

用户刚读完一批论文，脑中想法很多，需要把想法收敛成一个**可质疑、可实施、可验证**的框架设计。这不是写营销稿，也不是把论文里的模块名拼成一个新架构。

本项目的产出必须同时满足：
1. **忠实**：对论文的转述不夸大，区分“论文声称”“论文证据”“我们的推断”。
2. **可裁决**：每个借鉴来的机制都要给出采纳/改造/拒绝的结论和理由，不能只罗列。
3. **可验证**：关键主张要能落成对照实验或消融，不能只靠故事。

## 1. 证据等级（每条机制卡必须标注）

| 等级 | 含义 | 例子 |
|---|---|---|
| **A-实验** | 有对照实验且做消融/多任务/多seed；数字可核 | MLE-STAR 在 MLE-bench Lite 的消融；Novelty Search 的迷宫与双足实验 |
| **B-实验弱** | 有实验但样本少、无逐组件消融、或只有单领域 | Station 的少任务消融；Cogentic 的 5 个案例 |
| **C-框架/立场** | 提出机制但未做因果实验（或只是 position paper） | OpenAI CDC 提示词、多数“架构提案” |
| **D-自述/工程博客** | 机构或团队自述，无对照、无失败运行 | Anthropic 多智能体博客、Google Co-scientist 博客 |
| **E-推断** | 本团队基于以上材料做的设计推断，无直接文献支持 | “成果卡可替代…”“该机制能防坍塌” |

**铁律**：把 C/D 级材料写成 A 级结论，是本项目最严重的错误。每条结论句后可用方括号标等级，如“[A-实验]”。

## 2. 机制卡模板（文件内每个机制用同一结构）

```markdown
### 机制名（一句话）
- 来源：论文/博客 + 章节/页码（如 §3.2, Table 4）
- 证据等级：A/B/C/D/E
- 它到底怎么运作：（可实现的描述，不是口号。谁在什么时候读什么、写什么、决定什么）
- 论文报告的数字/现象：（有就写，没有写“未报告”）
- 适用条件与失效边界：（任务类型、预算、模型能力、评价器是否存在）
- 它解决的是哪个具体失败模式：
- 代价/副作用：（token、延迟、协调复杂度、收敛风险、奖励黑客）
- 对长城 Agent 的启示：[采纳 / 改造为 / 拒绝] + 一句理由
- 如果采纳，最小可验证形式是什么：
```

## 3. 原文与推断必须分开

- 引用论文时给章节号；数字必须来自原文，不许估算或“大致”。
- “论文没有做 X”要明确写“未报告/未做”，不要写成“无效”。
- 我们自己的设计建议放在单独小节，标 [E-推断]。

## 4. 禁止事项

- 禁止把“多智能体”“上下文工程”“知识沉淀”等词当成机制；必须写到可执行的动作粒度。
- 禁止用模块数量、角色数量、文档长度冒充研究贡献。
- 禁止编造实验数据、arXiv 编号、作者、页码。
- 禁止直接给用户一个“终极架构”；要给的是**有取舍的候选方案 + 判断依据 + 待验证清单**。
- 禁止把厂商宣传语（如“唯一可行路径”“全满贯”）当事实；引用时标注为自述。

## 5. 交付格式

- 中文，Markdown，写绝对路径的文件。
- 文件开头写：作者、日期、读了哪些材料（路径/URL）、阅读深度（全文/部分/摘要）。
- 正文按机制卡组织；末尾必须有：
  1. 本节最可靠的 3 条结论（带等级）
  2. 本节最不确定的 3 个判断
  3. 与用户已有设计（V1/V2/V3、探索架构草案 0.1）可能冲突的点
- 不要写超过 8000 字；宁可精确，不要铺陈。
