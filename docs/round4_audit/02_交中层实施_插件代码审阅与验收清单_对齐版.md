## 核心使命与整改原则

本清单的目标是：**彻底剥离通用代码中绑定的“数学建模竞赛 B 题特异性硬编码”，并将核心必经工具链打磨至“每一段均具备可机械验证的契约”。**
- **严守测试期暴露问题的原则**：测试阶段的核心价值是暴露真实故障，暂不引入单点故障后的全局静默降级逻辑；
- **各司其职、禁止越权**：严格区分“中层必须立即闭环的工程缺陷”与“需等待顶层拍板的科研语义”（顶层讨论与争议详见 [01_交顶层设计者_原文对照与架构讨论稿_对齐版.md](01_交顶层设计者_原文对照与架构讨论稿_对齐版.md)）；中层严禁擅自修改科学评估标准、依赖图逻辑与比对口径；
- **真实环境验收**：所有整改项必须在隔离测试夹具中用真实用例跑通，绝不能只靠静态类型声明打勾。

## 自动化测试现状与复核结论

在基准 `3dfa211` 下对现有测试套件进行了完整复核：
1. **Python 单元测试**：`unittest` 测试集 **17/17 项全部通过**。
2. **DSH 插件端到端（E2E）测试**：
   - 官方测试原样运行：**9 项通过，1 项在 20 秒超时被取消**；

## 二、正式评测与前线开发工具整改清单（E01–E07）

### E01 采编工具接口对齐与干预指令闭环（现场事故）
- **【现场证据】** 采编 Agent 在发布文献卡时发生 36 次失败（29 次枚举不合法，7 次摘要超长）。主控调用 `intervene` 发出修正指令，Agent 重新启动后依然重复报错。
- **【代码根因】**  
  1. `mcp_schema_docs.py` 将 `support_scope` 声明为普通的 string 类型；而服务端的 `tools_library.py#L144` 严格校验必须是 5 个固定英文枚举；
  2. 摘要 60–600 字的长度约束未在 Schema 的 `description` 或 JSON Schema 属性中明确暴露；
  3. 编排器在重启 Agent 会话时，未将缓存的 `steeredSessions` 指令拼接到 Agent 的系统提示词或首轮输入中。
- **【整改契约】**  
  1. 统一接口声明：以服务端代码与数据库 Check 约束为准，将 `support_scope`（枚举值）和 `abstract_md`（`minLength: 60, maxLength: 600`）完全写入 Schema 定义；
  2. 规范干预生命周期：实现“指令记录 $\rightarrow$ 实时投递到运行中会话 $\rightarrow$ 注入下次冷启动上下文 $\rightarrow$ Agent 执行后返回确认凭证”的全链路追踪。
- **【验收标准】** 隔离测试下，Agent 分别传入非法枚举与超长摘要，接口直接返回包含合法枚举列表的友好报错；发送定向干预后，验证 Agent 首轮交互确实收到了干预文本，并成功落库一张 400 字的合规文献卡。

### E02 解题模块提交路径、运行入口与本地自测契约对齐（现场事故）
- **【现场证据】** 探索者提交时产生大量 `MISSING_CANDIDATE_OUTPUT_FILE`；多个分支传入 `worktrees/分支名/...` 路径直接被拒。
- **【代码根因】**  
  1. `mcp_schema_docs.py#L30` 写明 `candidate_rel_path` 是“相对于整个工作区”，而 `tools_explorer.py#L108` 实际代码却从“当前分支的工作树根目录”解析，导致相对路径多拼了一层；
  2. 外部文档和自测 CLI 描述为“通过命令行 stdout 打印 JSON”，而实际沙箱 `isolated_runner.py#L46` 是通过 `importlib` 动态导入模块并调用 `run(public_input)` 函数，由沙箱将内存返回值写入临时文件。
- **【整改契约】**  
  1. 路径对齐：统一以分支工作树根为相对基准，并在 Schema 与报错信息中给出清晰的相对示例；
  2. 运行协议单一真理：正式规定解题模块的代码入口为 `def run(public_input: dict) -> dict`。提供一个跨分支共享的本地测试 CLI 脚本（如 `python -m tools.local_verify`），让 Agent 在提交前能在本地一键跑通完全同构的验证。
- **【验收标准】** 准备 4 组测试脚本（标准的 `run()` 脚本、仅有 CLI stdout 的脚本、语法错误脚本、依赖分支内部 `tools/` 辅助模块的脚本），提交正式评测；前两者应能明确识别并给出对应引导，后者能正确加载分支辅助模块并成功运行。

### E03 可信测试输入数据端到端链路传递（现场事故）
- **【现场证据】** `Obs-031` 的评测规格中包含完整的题目测试用例，候选模块计算正常，评测脚本却报“无可用输入”并判 0 分。
- **【代码根因】** 沙箱 Stage A 将题目输入包在 `spec.public_input` 传递给候选；进入 Stage B 评分时（`isolated_runner.py#L615`），评测脚本 `hook_Q1.py#L601` 先在候选输出中找原始输入，找不到又去查 `spec.sample` 和 `spec.input`，唯独漏掉了平台真实传递的 `public_input` 键。
- **【整改契约】**  
  1. 严格解耦输入数据源：题目的可信输入只能由评测规格提供，严禁从候选者的输出返回值中反向倒推输入；
  2. 统一键名规范：固定题目真实测试数据统一放置在 `evaluator_spec["public_input"]` 字段下。评测脚本基类必须提供标准取数辅助方法 `get_public_input(spec)`，消除各题脚本自行解析的割裂。
- **【验收标准】** 构造一份包含标准 `public_input` 的评测规格，执行 Stage A 和 Stage B，评测脚本能 100% 稳定读取输入并输出包含科学指标的评分回执，绝不再出现读取失败。

### E04 明确分离“基础设施故障”、“代码运行崩溃”与“科学评估结果”（现场事故）
- **【现场证据】** `run_isolated_eval` 工具调用返回 `ok: true`，但观测记录中却是 `EXECUTION_ERROR`；`Obs-031` 因评测脚本未取到输入直接被打上 `MEASURED_NON_IMPROVEMENT`（无改进），导致学术评估彻底失真。
- **【代码根因】** 沙箱将评测脚本返回 `passed=False` 一刀切归结为算法未达标；当评测脚本因自身异常或数据缺失返回默认零分时，平台缺乏“基础设施自身错误”的分类映射。
- **【整改契约】** 建立五级明确的执行与科学状态状态机：
  1. `INFRA_ERROR`：沙箱超时、依赖丢失、数据管道断开（严禁打上任何算法分数，不计入学术统计）；
  2. `CANDIDATE_CRASH`：候选代码自身抛出异常、语法错误或超时；
  3. `HOOK_INTERNAL_ERROR`：评测脚本自身抛出未捕获异常；
  4. `MEASURED_REJECTION`：评测正常执行，算法计算结果错误或未满足约束（有效负结果）；
  5. `VALID_IMPROVEMENT`：评测正常执行且指标达标。
- **【验收标准】** 依次注入沙箱中断、候选代码死循环、评测脚本除以零、候选给出错误解、候选给出正解 5 种场景，验证控制面与数据库能准确登记上述 5 种状态，杜绝任何将环境故障归为学术负结果的情况。

### E05 领域任务契约与多模态证据验证（现场及静态风险）
- **【现场证据】** Q1 要求输出区域顶点及证明或反例；而现场钩子只比对了少量汇总浮点数，且存在 `PASS(reference_only)`（仅参考复算通过）分支，导致数值比对通过并不能代表证明成立。
- **【代码根因】** 框架默认全流程仅支持“Python 返回 JSON $\rightarrow$ 单一标量分数比对”，无法原生承接数学证明证书、离散反例或 Pareto 前沿。
- **【整改契约】**  
  1. 梳理各子题的真实交付物契约：建立“任务需求 $\rightarrow$ 产物格式（代码/证书/JSON） $\rightarrow$ 验证机制 $\rightarrow$ 签发结论”映射表；
  2. 引入多模态验证器适配器：使得 Lean 形式化证明、解析推导手稿、离散反例能够与数值仿真一样，在框架中登记为合规证据。
- **【验收标准】** 使用 `evaluators/examples/` 下的 `formal_proof` 和 `pareto_frontier` 样例，通过统一的沙箱接口完成验证，系统能正确记录证明有效性或 Pareto 支配集。

### E06 评测缓存键复合生成与辅助依赖追踪（静态风险）
- **【代码根因】** 评测缓存的哈希计算（`tools_explorer.py#L145`）仅对单个候选 Python 入口文件计算 SHA256；而沙箱实际会拷贝整个分支的 `tools/` 目录。当探索者修改了依赖的辅助模块时，由于入口文件没变，系统依然命中旧的缓存结果。此外，缓存还将 `EXECUTION_ERROR` 永久缓存，导致偶发基础设施错误恢复后无法重试。
- **【整改契约】**  
  1. 复合指纹计算：缓存键必须由 `(候选入口哈希 + tools目录内容递归哈希 + evaluator_spec哈希 + 评测钩子SHA)` 四元组生成；
  2. 临时错误穿透：明确规定 `INFRA_ERROR` 和暂态执行错误不写入永久缓存，允许直接重新发起评测。
- **【验收标准】** 保持入口脚本不变，仅修改 `tools/` 目录下的一个函数实现；发起评测时系统应能识别指纹变化并触发真实重跑，不再误中旧缓存。

### E07 消除控制面轮询对重型评测逻辑的隐式触发（静态风险）
- **【代码根因】** 调度快照轮询（`control_plane_service.py#L381`）在执行状态检查时，会隐式调用 `_scan_invalid_protocol_hooks`，直接动态导入钩子、导入基线并执行 `baseline.run()`。一旦评测脚本较慢，前端每 3 秒一次的状态轮询就会拖死整个控制面。
- **【整改契约】** 读写彻底分离。状态轮询只能查询 SQLite 中已经持久化的健康标记字段；评测脚本与基线的健康检查只能在“注册时”、“显式升版时”或“外部工单触发时”以有界超时的独立任务运行，并写回健康状态表。
- **【验收标准】** 注入一个运行耗时 10 秒的恶意慢评测脚本，前端高频发起状态轮询请求，控制面 API 响应延迟保持在 50ms 以内，绝不发生卡顿阻塞。

## 三、宿主、MCP 与调度可靠性整改清单（E08–E15）

### E08 角色能力预检与本地插件打包交付清单（现场事故）
- **【现场证据】** 首批工造司 Agent 因缺失读写与 Shell 工具直接无法开工；插件 `package.json` 的 `files` 字段遗漏了 `presets/` 目录。
- **【代码根因】** `agent_session_host.js#L422` 的工具预检逻辑只覆盖了部分角色分支，且过度依赖本地软链接安装，导致标准打包发布时预设配置丢失。
- **【整改契约】**  
  1. 会话启动强制能力断言：Agent 启动前，宿主必须核验该角色声明的工具集是否在当前会话中 100% 挂载成功。若缺失，立即在启动收据中抛出具体缺失的工具列表并阻断派单；
  2. 修复 `package.json`：确保 `presets/` 目录及相关 YAML 规则文件包含在分发包中。
- **【验收标准】** 模拟干净无缓存的独立环境安装插件，启动全角色会话，验证工造司、采编、探索者均能按声明精准获取所需的完整工具列表。

### E09 JSON-RPC 桥接超时处理与状态一致性（静态风险）
- **【代码根因】** Node 与 Python 的 stdio 桥接默认超时为 60 秒，而 Python 底层沙箱单次评测允许运行最多 600 秒（`isolated_runner.py#L521`）。桥接一旦发生 60 秒超时，仅在 Node 端删除了等待项，Python 后台子进程仍在继续写入数据库，导致后续响应错位或静默丢包。
- **【整改契约】**  
  1. 超时时间对齐与分级：针对可能耗时的长任务（如评测），RPC 调用必须显式传递超时参数，使其与底层沙箱超时一致；
  2. 引入幂等任务凭据（Job Ticket）：长任务采用“发起任务返回 JobId $\rightarrow$ 异步轮询状态”的标准模式，避免单个 HTTP/stdio 连接长期挂起。
- **【验收标准】** 在夹具中模拟一个耗时 70 秒的合法任务，验证桥接不会在 60 秒时粗暴断开，能够稳定获取任务完成回执并保证数据库状态一致。

### E10 沙箱权限边界与角色执行隔离（现场及静态风险）
- **【代码根因】** 角色在 DSH 宿主层（Guard 插件）与 Python MCP 层的权限定义不统一，文档示例的虚构路径与真实路径割裂，导致 Agent 经常尝试越权探索。
- **【整改契约】** 建立单一权限真理源。统一以 Python 端的角色权限映射表为核心，DSH Guard 读取相同配置；在系统提示词中自动生成当前 Agent 实际拥有的可写目录与只读目录清单。
- **【验收标准】** 针对探索者 Agent，测试其读写自身工作区（允许）、读取公共库（允许）、写入他人分支（拦截）、尝试 Shell 逃逸（拦截），所有拦截均产生规范的权限审计日志。

### E11 调度状态机生命周期与并发安全（静态风险）
- **【代码根因】** 编排器在接收到 `start` 命令时（`index.js#L213`），若带目标参数会无条件重新执行数据库初始化，即使后台已有任务正在运行，导致活动纪元（Epoch）被强制冲刷覆盖。
- **【整改契约】** 强化调度生命周期状态机：严格定义 `UNINITIALIZED`、`INITIALIZING`、`IDLE`、`RUNNING`、`PAUSED`、`STOPPED`、`FAILED` 七种状态。若系统处于 `RUNNING` 状态，严禁直接执行初始化，必须显式调用停止并归档旧任务后方可重新开工。
- **【验收标准】** 在已有任务正在运行的状态下，连续并发触发 `start` 调用，系统必须安全拒绝后续请求并返回“任务已在运行中”的冲突错误码。

### E12 阶段流转强依赖数据库持久化回执（现场及静态风险）
- **【现场证据】** 现场出现多次在存在告警（ALERT）的情况下依然被签发放行；部分监控会话将后续阶段的告警带入前序阶段。
- **【代码根因】** 阶段推进过分依赖监控模型文字上的“PASSED”，缺少服务端代码层面的硬性前置断言复核（`tools_supervisory.py#L136`）。
- **【整改契约】** 实行“双保险”放行制度：阶段跃迁（如 Parse 0 进入 Stage 1）时，除了监控模型的审计陈述外，服务端代码必须对数据库做硬性谓词断言（例如：有效文献卡数 $\ge 1$、已注册题目验证器就绪、分支队列已初始化）。
- **【验收标准】** 人为将数据库中的前置条件置空，诱导监控模型输出“PASSED”，系统必须在服务端拦截该非法流转，拒绝推进阶段。

### E13 步数水位时钟计算与双阈值执行对齐（静态风险）
- **【代码根因】** DSH 宿主层使用的是投影 Token 窗口比例，而 Python 端使用的是运行配置的实际步数，两者在跨越 37%（阶段反思）和 70%（强制停笔交接）时计算基准打架。会话在反思未落库前就无条件告诉模型“已解锁”。
- **【整改契约】**  
  1. 统一以数据库持久化的实际交互轮次（Turn/Step）作为水位计算标准；
  2. 解锁原子化：只有当反思记录通过 `tools_companion.py#L245` 成功写入数据库后，才允许向 Agent 下发“已解锁阅读权限”的系统通知。
- **【验收标准】** 构造单步大 Token 和多步小 Token 的不同会话，验证系统在精确的步数比例处触发反思与停笔信号，并在反思提交失败时保持权限锁定。

### E14 分支异常退出捕获与自动打捞机制（静态风险）
- **【代码根因】** `pair_lifecycle.js#L112` 仅在显式捕获的异常终止时将节点推入打捞队列；如果在挂载、上下文延续或提交交接过程中抛出未处理异常，内存槽位被删除但数据库中该节点永远卡死在 `EXPLORING` 状态。
- **【整改契约】** 引入租约心跳超时检测（Heartbeat Lease）。若处于 `EXPLORING` 状态的节点在超过预定时间无活动，调度扫描器自动将其置为 `ABORTED` 并安全推入后勤打捞队列，释放分配的并发槽位。
- **【验收标准】** 人为强杀一个正在探索的 Agent 会话进程，验证调度器在超时后能自动将该节点状态更新并交由后勤模块接管，不会造成系统永久卡顿。

### E15 控制台工作区路由与前端轮询时序保护（静态风险）
- **【代码根因】** 前端每 3 秒发起一次全量轮询，缺少请求序列号与防乱序机制；当网络延迟导致旧的慢响应晚于新响应到达时，前端 UI 状态会被旧数据倒灌覆盖。
- **【整改契约】**  
  1. 请求加时间戳与版本号：前端自动丢弃版本号低于当前已渲染版本的响应；
  2. 控制台路由加工作区硬校验：精确匹配工作区路径，禁止模糊回退到其他控制器。
- **【验收标准】** 在网络延迟夹具中模拟响应乱序到达（响应 A 延迟 2 秒，响应 B 延迟 0.1 秒），验证前端界面始终渲染最新的响应 B 数据，不发生闪烁倒退。

## 四、图书馆、后勤、规约与数据完整性整改清单（E16–E22）

### E16 修复 SQLite FTS5 全文搜索多关键词语法崩溃（现场及复核确认）
- **【现场证据】** 探索者调用 `query_library_catalog` 时多次抛出 SQLite 语法错误。经现有用例复核：**单词 `Jung` 正常，而传入 `Jung bound` 或中文 `最小 圆` 时必定在第二词附近触发 FTS5 语法崩溃**！
- **【代码根因】** `db_schema.py#L812` 的 `sanitize_fts5_query` 函数对每个拆分出的关键词分别包裹了一对括号，且中间直接用空格简单拼接，导致生成的 FTS5 表达式格式非法。
- **【整改契约】** 彻底重构 `sanitize_fts5_query` 函数：
  1. 过滤特殊字符与运算符；
  2. 对每个搜索词用双引号安全转义；
  3. 多个词之间使用 FTS5 标准的 `AND` 逻辑运算符进行连接（例如将输入转换为 `"Jung" AND "bound"`）。
- **【验收标准】** 编写针对 FTS5 的专项测试集，覆盖中文多词（如“最小覆盖圆”）、英文多词、带括号/引号特殊符号、空字符串及超长查询，所有用例均需安全解析并返回正确查询结果，崩溃率彻底归零。

### E17 剔除通用 AST 代码检查中的赛题特异性黑名单（静态直接证据）
- **【代码根因】** `mcp_core_helpers.py#L472` 中的 `validate_baseline_isolation_ast` 函数，硬编码了 `Q1...Q9` 并在代码中写死：**只要子题是 `Q3`，就绝对禁止出现包含 `second_pass` 的函数名或变量名**。这是为了防止当年 B 题 Q3 混入 Q4 逻辑而留下的特化硬编码，完全破坏了通用性。
- **【整改契约】** 彻底移除函数中针对 `Q3` 和 `second_pass` 的特定文字黑名单。基线脚本的隔离检查回归本质：仅通过 AST 检查是否跨子题非法 `import` 其他题目目录下的模块。
- **【验收标准】** 创建一个包含 `def second_pass_optimization():` 的合法 Q3 基线脚本，提交 AST 校验，系统应顺利放行，不再报非法机制拦截错误。

### E18 评测设施保真度实测与能力就绪准入（静态与设计待定）
- **【代码根因】** 评测注册（`tools_works.py#L231`）直接采信调用方传入的静态字段 `fidelity_max_error_pct`，系统完全未做物理实测。
- **【整改契约】** 中层明确区分“申报数值”与“实测数值”。若当前任务协议声明需要做保真度检验，注册流程必须使用基准输入实际运行基线与评测器，由平台独立计算并持久化真实的误差百分比。
- **【验收标准】** 注册评测器时，传入虚假声明的“误差 1%”，而实际运行测试用例产出误差为 8%，系统应能识别并根据阈值（<5%）拒绝该注册请求。

### E19 修复子题依赖并集锁死与送审通道解耦（现场事故）
- **【现场证据】** 现场 Q1 出现故障时，完全不依赖 Q1 的其他独立路线全部被连带锁死；后勤送审时非数值形式的成果无法提交。
- **【代码根因】**  
  1. `control_plane_service.py#L322` 将同题所有流派的前置依赖取并集锁死整题；
  2. `tools_logistics.py#L325` 将常规送审硬编码为必须有 `VALID && passed=1` 的观测。
- **【整改契约】**

  2. 扩展送审适配器：送审检查除布尔值通过外，支持接收经独立验证器签发的“证明证书哈希”或“反例有效性凭据”。
- **【验收标准】** 针对同一子题注册两个流派，流派 A 依赖 Q1，流派 B 无依赖。在 Q1 尚未出成果时，验证流派 B 能被正常调度执行。

### E20 工作树真实现代化与文件事务一致性（静态风险）
- **【代码根因】** `tools_logistics.py#L563` 声明为“Git Worktree 隔离”，实际仅用 `mkdir` 创建目录并做文件拷贝，未执行真正的 Git worktree 生命周期管理，且文件操作与数据库事务没有统一回滚保证。
- **【整改契约】**

- **【验收标准】** 人为触发目录创建权限失败，验证数据库中的分支表不会生成多余脏数据，保持状态绝对清洁。

### E21 两阶段同行盲审与证据版本追溯（静态风险）
- **【代码根因】** 审稿入账与终审（`tools_library.py#L343, L569`）未处理“手稿排队期间其绑定的旧观测被评测器升版撤回”的竞态条件。

- **【验收标准】** 模拟一条手稿在送审后，其底层 Obs 被标记为已撤回；终审模型尝试批准该手稿入库时，系统强制拦截并提示证据已失效。

### E22 课题终局结题与交付物原子化导出（静态与测试未闭环）
- **【代码根因】** 终局阶段中，方案择优模块（Comparator）的结构化对比数据未作为最终导出的强制校验输入；且交付物按文件逐个写入，若后段报错会残留半截残缺目录。
- **【整改契约】**

- **【验收标准】** 模拟导出过程中在生成最后一篇文档时触发异常，验证工作区不会残留半成品的垃圾目录，系统能准确回滚并报错。

## 五、评测演化（RQGM）与工单机制整改清单（E23–E27）

### E23 彻底剥离“Bug 修复回归”与“学术标准重构”的升版门禁（现场事故）
- **【现场证据】** Q1 v4 成功修掉了空载荷误判漏洞，但因为在旧锚点上的指标与老版本持平（`BB_eps` 平局），被平台判定“无改进”直接拒绝升版；末段在无统一考卷的前提下，拿小样本和大样本的孤立计数（`0.7169` 对 `0.9757`）比大小。
- **【代码根因】** `tools_works.py#L494` 强制要求挑战者的新脚本在指标上必须严格大于在位者，将系统 Bug 修复与学术模型演进混为一谈；且在无锚点时盲目相信自报比例。
- **【整改契约】** 实行双通道升版判定：
  1. **通道 A：缺陷修复（Bugfix Patch）**  
     提交针对具体 Bug 的回归测试集（包含原本误判通过的负例用例）。验证老脚本在新测试集上失败、新脚本全通，且在历史黄金测试集上零回归，**直接批准升版替换，不参与任何刷分比对**；
  2. **通道 B：标准重大变更（Major Evolution）**  
     必须提供同源基准测试集实测，冻结旧版本纪元并建立重评映射。
- **【验收标准】** 模拟一个存在空输入误判漏洞的老评测器，提交修复版评测脚本及对应的负例测试用例；系统走 Bugfix 校验通道顺利批准升版，不再报平局被拒。

### E24 评测器健康度诊断与科学结果解耦（现场及静态风险）
- **【代码根因】** 控制面熔断器（`control_plane_service.py#L381`）将“无可用输入”这种评测脚本的读取 Bug，登记为“算法无改进”，直接避开了熔断检测；反过来，又将整道题跨版本的历史成功样本累计起来计算健康度，导致老版本的历史成功掩盖了新版本的致命 Bug。
- **【整改契约】**  
  1. 熔断基于当前在位版本：健康度统计仅计算当前在位评测器版本生命周期内的样本；
  2. 连续基础设施故障立即熔断：只要连续出现 3 次因评测脚本自身引发的崩溃或取数异常，立即对该子题触发熔断告警并挂起探索。
- **【验收标准】** 注入一个读取字段错误的在位钩子，连续发起 3 次评测，系统必须精准触发子题评测熔断，不再继续派单浪费算力。

### E25 受控重评的数据留痕与版本一致性（静态风险）
- **【代码根因】** 评测器升级后触发历史成果重评时（`tools_works.py#L597`），代码直接覆盖了原观测记录的指标与判定，但未同步更新诊断理由（`validity_reason`），导致数据库中出现“判定与原因相互矛盾”的脏数据。
- **【整改契约】** 重评操作禁止原地物理覆盖。系统必须保留原观测记录的历史快照，生成一条带新版本标识的全新重评记录，并在历史记录上标记“已由版本 X 重评”。
- **【验收标准】** 触发一次重评操作，检查数据库，验证能够同时查到原始历史判定与重评后的全新判定，审计证据链完整无断层。

### E26 抑制工单爆炸风暴与引入收敛闭环（现场事故）
- **【现场证据】** 现场从第 2 次评测失败起，每次报错均自动创建一张新工单，一口气刷出了 22 张未关闭的重复自动工单，把工造司唤醒打爆。
- **【代码根因】** `tools_explorer.py#L299` 缺乏针对相同根因故障的去重聚合逻辑，同一个接口报错在每次评测重试时均无条件插入新工单。
- **【整改契约】**  
  1. 工单指纹去重（Deduplication）：基于 `(question_id, error_type, root_cause_signature)` 计算指纹；若同类工单已存在且处于 `OPEN` 状态，只更新命中计数与最后发生时间，严禁无休止创建新工单；
  2. 自动解决闭环：当新版评测器升级成功并在真实测试用例中验证通过后，关联的 OPEN 工单自动批量变更为 `RESOLVED`。
- **【验收标准】** 连续模拟 10 次完全相同的输入读取异常，验证系统仅创建 1 张工单且计数累加为 10；评测器修复升版后，该工单自动归档关闭。

### E27 逐一核对 31 个窄工具的 Schema、声明与 Python 实现（复核基准）
经从 Node 宿主（`prompts.js#L31`）与 Python 核心（`greatwall_core_mcp.py#L74`）的逐项机械比对：**31 个窄工具名称齐全，7 个角色的白名单分配一致**。但在参数定义上，检出 **7 个工具存在“Schema 声明为必填（required），但 Python 代码实际提供默认值”的口径差异**。
- **【整改契约】** 针对以下 7 个工具，逐项统一说明文档与代码默认值逻辑：

| 工具名称 | 接口文档/Schema 要求显式传参 | Python 代码底层默认值 | 整改处置规范 |
|---|---|---|---|
| `run_isolated_eval` | `declared_refs` 标记为必填 | `declared_refs=None` | **保留 Schema 约束**：强制模型声明参考依据，代码层在空值时友好报错。 |
| `query_library_catalog` | `keyword`, `scope` 必填 | `keyword="", scope="ALL"` | **统一口径**：在 Schema 中将二者明确标记为可选（Optional）。 |
