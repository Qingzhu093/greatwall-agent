## 核心审阅结论（一句话省流）

> 第四轮测试的停摆，证明了一个残酷的现实：**哪怕中层实施团队 100% 毫无偏差地按照现存文档施工，系统也必定会在特定的研究场景下卡死！**

### 1. 把“有参考答案的任务”当成所有科学研究的常态

#### 【原文寻章摘句与精准出处】
- **出处 A**：[`docs/architecture/04_十三篇前沿论文深度解惑与V6Up架构融合专报.md#L38`](../architecture/04_十三篇前沿论文深度解惑与V6Up架构融合专报.md#L38)

- **出处 B**：[`docs/architecture/04_十三篇前沿论文深度解惑与V6Up架构融合专报.md#L258-L266`](../architecture/04_十三篇前沿论文深度解惑与V6Up架构融合专报.md#L258-L266) (§3.5 节)  
  > 原文：“Stage 1 必须为每一道子题（无论纯数学还是数值优化）注册独立的验证钩子与独立的零号基线……”
- **出处 C**：[`docs/agent_kb/04_工造司与评测_共享探针_可插拔验证钩子与RQGM受控纪元演化.md#L24-L28`](../agent_kb/04_工造司与评测_共享探针_可插拔验证钩子与RQGM受控纪元演化.md#L24-L28)  
  > 原文：“每一个子题 $Q_i$ 必须拥有自己独立的验证钩子 `evaluators/hooks/hook_<question_id>.py` 与独立的零号基线 `baselines/baseline_<question_id>.py`！……纯理论必检清单包括：量纲齐次性、极限边界行为、SymPy 残差……以及**与公开物理基准曲线的残差剖面对比**。”

#### 【过窄与失灵分析】
上述条款强行假定：任何科研任务在开局前，世界上都必须已经存在一份已知的“参考答案”或“公开基准曲线”，并假定工造司能在选手做题前凭空写出一个判题程序。
- 当任务是**证明一个前沿数学猜想**时，只有命题定义与推导公理，根本不存在所谓的“零号基线”；
- 开放性机理探索中，往往需要等到前线实验采集到第一批物理数据后，具体的评估维度才能被定义；
- 即便在国赛 B 题 Q1 中，几何算法求解与“给出一般性的数学证明或反例”也是两码事。工造司根本无法按文档要求提供统一的基线。

#### 【应修改的顶层条款（人话重写）】
> **修订方案**：修改《04 专报》第 107–115 行与《agent_kb 04》第 24 行。  
> 明确“Parse 0 阶段的准入交付物由课题类型决定”：
> - 存在已知参考解的数值任务，才强制提供基线与残差定义；
> - 纯理论证明任务，交付物为“清晰的形式命题定义、公理前提与证书检验规则”；
> - 开放探索任务，交付物为“可证伪假设、已知边界与初验判定逻辑”，**绝不强制要求无参考任务凭空捏造零号基线**。

### 2. 把国赛一次模拟器失真的个案教训，写成了全平台的统一硬指标“误差 < 5%”

#### 【原文寻章摘句与精准出处】
- **出处 A**：[`docs/architecture/04_十三篇前沿论文深度解惑与V6Up架构融合专报.md#L156`](../architecture/04_十三篇前沿论文深度解惑与V6Up架构融合专报.md#L156) (§2.2 节)  
  > 原文：“根治 P25：Stage 1 仿真器与原始物理场分布差异必须小于 5%（KS 检验相对误差），严防劣质仿真器带病锁死纪元……”
- **出处 B**：[`docs/agent_kb/04_工造司与评测_共享探针_可插拔验证钩子与RQGM受控纪元演化.md#L28`](../agent_kb/04_工造司与评测_共享探针_可插拔验证钩子与RQGM受控纪元演化.md#L28)  
  > 原文：“任何经验/物理仿真环境在锁定 `eval_epoch_version = 1` 之前，必须与题面给定的锚点矩/经验分位数做 Kolmogorov-Smirnov 或相对矩误差核验；**最大关键分布误差 $\ge 5\%$ 时，代码层硬性拒绝解锁 Stage 2 高并发派单**！”

#### 【过窄与失灵分析】
这个 5% 的阈值，直接源于历史第二轮测试中国赛 B 题 Q3 仿真器误差场被过度拉伸截断（24.8% 测点饱和在 $\pm 1^\circ$）的具体翻车教训。
- 把它硬编码成全平台“任何物理仿真环境”的通用门槛极度荒谬：Kolmogorov-Smirnov 的统计距离、均方根误差（RMSE）与一阶矩相对偏差，物理含义完全不同；
- 一个模型可能整体均值拟合得极好（误差 < 2%），但在极端尾部事件上严重失真；反之，当物理参考值接近于零时，相对误差随便一算就是几百倍，导致合规的物理仿真器被 5% 门槛无差别扼杀。

#### 【应修改的顶层条款（人话重写）】
> **修订方案**：修改《agent_kb 04》第 28 行。  
> 废除“全局固定 5%”的死规矩。保真度校验仅在“提供了基准真实分布”的特定物理任务中启用；其评价指标（KS 距离、特定阶矩误差、置信区间）、校验区域（关注均值还是关注尾部）以及容忍阈值，**必须由该具体课题的验证协议明确指定，平台只负责执行该课题指定的测量规则**。

### 3. 把“按题适配的验证器”，写死了必须是“复制 Python 脚本运行”的单一形态

#### 【原文寻章摘句与精准出处】
- **出处 A**：[`docs/architecture/04_十三篇前沿论文深度解惑与V6Up架构融合专报.md#L160-L162, L281-L283`](../architecture/04_十三篇前沿论文深度解惑与V6Up架构融合专报.md#L160)  
  > 原文：“通用底座极薄……按题可插拔验证钩子必须作为 `evaluators/hooks/hook_<question_id>.py` 物理存在……最小观测七要素固定为候选代码 SHA、Worktree 相对路径、Stage A 输出 JSON、验证钩子 SHA……”
- **出处 B**：[`docs/agent_kb/04_工造司与评测_共享探针_可插拔验证钩子与RQGM受控纪元演化.md#L37-L42`](../agent_kb/04_工造司与评测_共享探针_可插拔验证钩子与RQGM受控纪元演化.md#L37-L42)  
  > 原文：“Stage A 与 Stage B 严格分离……Stage A 必须写入 `eval_artifacts/<obs_id>/stage_a_output.json`……通用健壮性拦截（NaN/Inf、**常数/全零退化解**及中位数突变步长噪声预警）……”

#### 【过窄与失灵分析】
顶层一边宣扬“容器极薄、Plugin is everything”，一边在数据契约上定死了：选手的产物必须是一个可以被沙箱执行的 Python 脚本，必须由系统调 `run()` 产出一段 JSON，且一刀切拦截“常数/全零解”。
- 实际上，形式化数学证明交付的是 `.lean` 源码文件或证明检查器证书（Proof Certificate）；真实物理实验交付的是传感器原始 CSV 或不可篡改的数据包；
- 在许多前沿科研中（如对称破缺证明、零偏解探索、真空态计算），**“全零解”或“常数场”恰恰是极其关键的正确基态**，通用拦截直接把正解判定成了退化错误。

#### 【应修改的顶层条款（人话重写）】
> **修订方案**：修改《agent_kb 04》第 41 行。  
> 底座数据总线仅规定“主张与凭证绑定”的通用元数据，产物形态允许为“Python 返回值、独立证明证书文件、实验观测数据包或离散反例结构”。常数解、零解是否属于退化错误，由子题验证规则自行判定，底座禁止越权全局拦截。

### 4. 把防止同质化探索的愿景，机械地写成了“开局每题必须强凑出两条互斥路线”

#### 【原文寻章摘句与精准出处】
- **出处 A**：[`docs/architecture/04_十三篇前沿论文深度解惑与V6Up架构融合专报.md#L113, L228-L230`](../architecture/04_十三篇前沿论文深度解惑与V6Up架构融合专报.md#L113)  
  > 原文：“Stage 1 结束前，必须为各子题登记 $\ge 2$ 个底层思想互斥的初始学派……每个活跃子题开局必须登记两条互斥方法并发探索，防止收敛到局部最优……”
- **出处 B**：[`docs/architecture/手写project.md#L124-L126`](../architecture/手写project.md#L124)  
  > 原文：“我们假设不缺算力……多路并发是克服大模型单一思维倾向的核心手段……”

#### 【过窄与失灵分析】
手写纲领提倡多路探索是为了防思维定势。但被写成硬性准入规则后，变成了一场官僚灾难：
- 很多科研子题在开局阶段，只有一项必须首先完成的“公共数据标定”或“基础引理推导”，此时根本不存在两条所谓“互斥的路线”；
- 强制要求填报两条互斥路线，直接逼迫调度 Agent 编造词藻不同但底层实质完全相同的“伪互斥学派”；
- 当遇到单次成本极高的仿真或昂贵算力时，硬性双路并发直接导致算力浪费。

#### 【应修改的顶层条款（人话重写）】
> **修订方案**：修改《04 专报》第 113 行。  
> 明确“多样性是调度原则，最低并发学派数是资源和课题配置项”。允许特定课题声明为“串行单兵攻坚”或“互补验证模式”（如一路构造正向证明、一路构造反例证伪），废除开局无条件强凑两条互斥路线的硬卡阻断。

### 5. 把“先跑通一次正式评测”，当成所有探索者开始反思（37%）与交接（70%）的铁门槛

#### 【原文寻章摘句与精准出处】
- **出处 A**：[`docs/architecture/04_十三篇前沿论文深度解惑与V6Up架构融合专报.md#L218-L224`](../architecture/04_十三篇前沿论文深度解惑与V6Up架构融合专报.md#L218) (§3.3 节)  
  > 原文：“37% 压力水位（185,000 tokens）且 `eval_count >= 1`（跑通至少一次真实实验）才允许触发反思并解锁内藏……”
- **出处 B**：[`docs/architecture/09_V6Up_v2.2_实施侧工程交接与系统开发总说明书.md#L33`](../architecture/09_V6Up_v2.2_实施侧工程交接与系统开发总说明书.md#L33) (清洗 2)  
  > 原文：“统一直算 `pressure_tokens / 500,000`（`37% = 185,000` 且 `eval_count >= 1`；`70% = 350,000`）……”
- **出处 C**：[`docs/agent_kb/02_后勤与谱系_上下文时钟_一对一伴随_四级分诊与五车道复苏.md#L33-L37`](../agent_kb/02_后勤与谱系_上下文时钟_一对一伴随_四级分诊与五车道复苏.md#L33-L37)  
  > 原文：“零实测崩溃（`eval_count == 0`）：即使有代码草稿，也不得写入正式 Handover……仅归档为 scratch_log……”

#### 【过窄与失灵分析】
这一机制的初衷是防止 Agent 光空谈不写代码实测。但它把“实测”窄化为了“调一次 `run_isolated_eval` 且产生一条 Obs”：
- 如果一个 Agent 在前半程完成了一篇极其严密的解析数学推导、数学反例证明或大规模离散搜索，由于现存评测脚本不支持这些形式，其 `eval_count` 永远是 0；
- 到了 37% 水位，因为没有所谓的“实测”，系统直接剥夺其反思与查阅参考资料的权利；到了 70% 水位，哪怕其草稿中有极其珍贵的数学思想，由于 `eval_count == 0`，系统将其全部当成垃圾丢入 `scratch_log`，禁止生成正式交接。

#### 【应修改的顶层条款（人话重写）】
> **修订方案**：修改《09 说明书》第 33 行与《agent_kb 02》第 34 行。  
> 明确“有效科研产出”的范畴：只要 Agent 在工作区留下了**经伴随助手核验自洽的数学推导手稿、可复核的反例数据或阶段性实验日志**，即便尚未触发或无需触发沙箱打分，同样视为完成一次实质探索，正常享有反思与正式谱系交接资格。

### 6. 把“全卷必答、拼题择优、封箱出论文”，当成了系统唯一的终局出口

#### 【原文寻章摘句与精准出处】

  > 原文：“check_stage2_closure_gate 硬锁：各必答题必须均有 `L3_VERIFIED >= 1`，方可解锁 Stage 3 终局交付……Comparator 跨流派横向择优、Formal Writer 组装论文……”
- **出处 B**：[`docs/architecture/09_V6Up_v2.2_实施侧工程交接与系统开发总说明书.md#L38`](../architecture/09_V6Up_v2.2_实施侧工程交接与系统开发总说明书.md#L38) (拍板 3)  
  > 原文：“全题 `L3_VERIFIED >= 1` 放行后……导出 `<workspace>/final_delivery/` 五件套……”
- **出处 C**：[`docs/agent_kb/03_中央图书馆_三本账_两阶段物理盲审_Auditor二次打捞与依赖撤回.md#L160`](../agent_kb/03_中央图书馆_三本账_两阶段物理盲审_Auditor二次打捞与依赖撤回.md#L160)  
  > 原文：“结题硬锁：全卷必答题有效 L3 覆盖率必须达 100%……”

#### 【过窄与失灵分析】
这是典型的“全国大学生数学建模竞赛 B 题全卷提交”思维：
- 在真实前沿探索中，课题可能最终**证伪了原猜想（确定无解）**，或者在预算耗尽时给出了高质量的**部分阶段性结论**，亦或是输出了**不可全序比较的 Pareto 最优解集**；
- 顶层设计死死咬定“必须每道题都拿到一个通过盲审的 L3，才能进入 Stage 3 输出交付物”，导致遇到证伪任务或算力耗尽时，系统永远卡死在 Stage 2 的死循环中，无法体面归档结题。
