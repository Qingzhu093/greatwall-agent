## 一、对报告 §3.2 所谓“4 个顶层设计病灶”的逐条驳斥与定性

第五轮实测中，长城插件在第 6–7 分钟即实质性瘫痪，85% 以上的请求烧在僵尸空转与死循环风暴里。把这场事故定性为“顶层设计过重”是**倒果为因**。下面按源码与顶层文档逐条核定责任边界：

### 1. 驳斥“病灶 1：10 跳刚性串行流水线”——偷换概念
- **事实核对**：V6-Up v3.0 顶层架构设计的是**异步事件驱动池 + 多分支 Git Worktree 并发探索拓扑**，而非报告中强行画成的一条“10 跳刚性串行流水线”。
- **真实因果**：第五轮“0 个 L3”根本不是流程太长导致的，而是第 6 分钟因为 `fork_branch` 未向 worktree 挂载公共题面、沙箱又拦死了外部读路径，导致 Q2/Q3/Q4 全部跑偏解成 Q1；紧接着第 7 分钟主控发 `steer` 广播吵醒伴随、把 6 个在跑节点全部提前关停，旧探索者又不查 DB 终态变成僵尸占满全部 6 个槽位，导致后续 30 分钟全员饿死。**连第一跳（正常读题与跑通）都被工程 Bug 拦断了，拿“0 个 L3”指责后续盲审与治理流程过长，逻辑不成立。**
- **严正澄清“主控 9 分钟写完 40 页论文”的错误类比**：主控直接捞半成品拼出 40 页论文，本质是**绕过独立盲审与真实可复现验证的“无评审草稿”**。多智能体科学发现系统的价值底线是可复现、可审计的真实发现（L3），绝不能用“跳过同行评审的写稿速度”反过来否定盲审门槛。

### 2. 纠正并裁决“病灶 2：单节点保活休眠伴随是过度设计”——找错了病根
- **顶层规格确认**：单节点 `lineage_companion` 在同一节点内执行 `PRE_SPAWN → 挂起保活 → REFLECT_37 → 挂起保活 → HANDOFF_70 → 销毁`（**方案 A**），确实是最新版顶层架构白皮书（`04`）与零前提工程总说明书（`09`）的正式要求。顶层**坚持方案 A**，不降级为无状态一次性伴随。
- **真正病根不在伴随保活，而在中层私造的“无差别 `steer` 广播池”**：
  - 核对 [orchestrator.js](file:///d:/antigravity/长城agent设计v6up（Gemini负责）/greatwall-v6up/dsh_plugin/lib/orchestrator.js#L127-L153) 与 [orchestrator.js](file:///d:/antigravity/长城agent设计v6up（Gemini负责）/greatwall-v6up/dsh_plugin/lib/orchestrator.js#L323-L351)：当 `targetType === 'global'` 时，`_interventionMatchesSession` 无条件返回 `true`，直接遍历整个 `this.liveSessions` 向所有在线会话塞入 `agent.steer(...)`。
  - 这不只是把伴随吵醒了——如果其他角色当时恰好在运行，**全员都会一起炸**：
    - **`library_verifier`（盲审官）**正在独立空白沙箱盲审，收到人类业务纠偏广播，**当场击穿盲审隔离宪法**；
    - **`supervisory_committee`（监察委）**正在跑合规心跳审计，收到业务纠偏指令，无业务权限却被强行干扰；
    - **`logistics_coordinator`（后勤总管）/ `works_engineer`（仪器科）/ `library_surveyor`（采编）**正在执行原子短事务，中途被 `steer` 打断直接导致状态漂移或半成品落库。
  - **结论**：第五轮是 `lineage_companion` 率先替全员“踩雷”暴露了这个结构性后门。解决方案不是砍掉单节点伴随，也不是给伴随打补丁，而是**直接删掉整个 `steer` 广播池**（详见 §二）。

### 3. 驳斥“病灶 3：硬编码 500k 与 37%/70% 反科研直觉”——混淆了工程失真与架构原则
- **500k 窗口失真是工程 Bug**：你们在 [index.js](file:///d:/antigravity/长城agent设计v6up（Gemini负责）/greatwall-v6up/dsh_plugin/lib/index.js#L280-L289) 只读 `exec?.agent?.options`（拿不到 DSH UI 的 `model/selection`），把全部子代理漏进了真实窗口仅 **272k** 的第三方中转模型 `thingo-gpt/gpt-6.2-sol`，却没按真实模型窗口动态计算预算上限。这是路由与窗口读取 Bug，不是 37%/70% 机制本身的错。
- **37%/70% 机制的真实意图**：37% 反思与 70% 强制清醒交接是为了防止长上下文注意力退化与上下文腐烂，**不是要求模型“硬凑字数”**。
- **问题出在中层硬编码的死催循环**：[pair_lifecycle.js](file:///d:/antigravity/长城agent设计v6up（Gemini负责）/greatwall-v6up/dsh_plugin/lib/pair_lifecycle.js#L319-L329) 硬写了 `'未满 70% 不准停工'` 强迫续推，甚至在探索者已完成阶段性可验证结论或收到外部终止时仍机械催促。
- **整改口径**：**保留 37% 反思与 70% 防爆红线**，窗口基数改为动态读取真实绑定模型的上下文窗口（并允许显式配置上限）；同时允许探索者在产出完整可验证工件或控制面下发收口信号时优雅提前交接，不再机械死催。

### 4. 定性“病灶 4：资源护栏与治理防自旋”——100% 属于工程底线
- 显式模型绑定与启动校验、列名一致性（[orchestrator.js](file:///d:/antigravity/长城agent设计v6up（Gemini负责）/greatwall-v6up/dsh_plugin/lib/orchestrator.js#L768) 错写 `r.request_id` 而 DB 返回 `r.req_id`）、`works_engineer` 缺少关闭工单工具、节点已终态但循环不查 DB、治理循环缺少幂等熔断——**这些全部是中层工程实现的硬底线与测试前核验疏漏，绝非顶层设计缺陷**。本次全部纳入 P0 止血清单，立刻修透，不再扯皮。

## 二、顶层架构正式裁决：删掉 `steer` 广播，回归「公开题面/裁决文档 + 极简启停」

从第一性原理审视：第五轮雪崩的本质，是硬塞了一套多余的 `steer` 聊天广播机制。**既然探索者本来就是短命可抛弃节点，删掉这个多余机制即可，绝不再叠床架屋造新结构。**

### 为什么极简方案就够了？
1. **彻底删除 `steer` 后，根本没必要再拆分什么“会话池”**：
   - `liveSessions` 原本只是登记在线进程以便 `stopBackground` / `disposeAll` 统一清理和监控展示的普通表。只要不再有 `intervene(action="steer")` 去遍历它乱发消息，它就不会误伤任何角色，无需人为拆成多个会话池徒增复杂度。
2. **所有 Agent 本就应该能读到完整公开题面与补充裁决文档**：
   - 盲审隔离的是**作者身份与未提交草稿**，不是隔离题目本身。
   - 只要公开题面、公开输入以及人类/主控追加的**《补充裁决文档》**（如赛题澄清、约束修正、方向说明）统一放在公共只读输入区（并挂载/可见于所有工作区），所有角色天然都能读到最新完整真源，根本不需要另建一套指令表或消息路由。
3. **跑偏了直接杀节点，不搞“边飞边喊话”**：
   - 单个探索者满 70% 上下文就会自然交接销毁，寿命极短。如果发现跑偏，主控直接 `abort_node` 杀掉重开，比飞行中 `steer` 喊话可靠一百倍。

### 正式架构裁决（自本日起生效，写死入代码）

1. **整块删除 `steer` 广播机制**：
   - 删除 `orchestrator.js` 中的 `intervene(action="steer")`、`_interventionMatchesSession`、`_formatInterventionsForTarget`、`_appendInterventions` 以及内存数组 `this._interventions`。
   - 严禁任何外部入口向正在运行的子代理会话发送 `agent.steer(...)` 喊话。
2. **统一公开输入与裁决文档只读可见**：
   - 公开题面、公开输入数据以及主控/人类新增的《补充裁决文档》，作为唯一公开事实源，保证**所有角色**（含探索者 worktree 与各类治理/盲审角色）开箱即可只读访问（仅隔离 `_hidden*`、其他分支草稿等受保护目录）。
3. **主控只需保留最朴素的确定性控制动作**：
   - `pause()` / `resume()`：冻结与恢复事件池；
   - 直接补充/更新公开《裁决文档》或公开输入文件；
   - `abort_node(node_id)`：精准终止跑偏探索者 + 同步销毁其私有伴随 + 在 SQLite 标终态释放槽位；
   - `human_stop(note)`：显式叫停并走合法收口导出 Stage 3。

> **极简操作流**：
> - 温和纠偏/补充说明 → 主控直接加一份公开《裁决文档》，旧节点自然跑完，新节点与各角色自动读到；
> - 严重跑偏（如第五轮做错题）→ `pause` → 补齐公开输入/裁决文档 → `abort_node` 杀掉跑偏节点 → `resume`。零广播、零额外机制、零连坐风险。

## 三、为什么“多轮审阅 + 单测全绿”仍拦不住这 7 个 Bug？

必须点破研发验证流程的盲区，否则改完这 7 个还会爆下 7 个：
1. **静态审阅看不到跨时间线并发碰撞**：单看“伴随保活”没问题，单看“`intervene` 广播”也没问题，单看“沙箱防越权”没问题，单看“建 worktree”也没问题——但放到同一条时间线上，两两相撞瞬间引爆。
2. **两端各写各的 Mock 掩盖了真实契约错位**：Python 单测验的是 `req_id`，JS 单测自己手写 Mock 喂了 `request_id`，两边全绿，一联调直接拼出 `[null]`；`exec.agent.options` 在单测里塞了假对象，一进真实 DSH 桌面端变成 `{}`。

**因此，从第六轮起立下硬性研发门禁**：
- 不再靠昂贵的真题实战去排低级集成 Bug；
- **强制建设「2 秒零费用全链路沙盘测试（Fake-LLM Integration Harness）」**：用毫秒级可控剧本假模型（Stub LLM）驱动**真实的 `GreatwallOrchestrator` + 真实的 Python MCP Control Plane + 真实的 SQLite WAL + 真实的 `read_isolated_sandbox` + 真实的 `fork_branch`**，每次改动必须在 2 秒内跑通完整闭环与故障回归剧本。
